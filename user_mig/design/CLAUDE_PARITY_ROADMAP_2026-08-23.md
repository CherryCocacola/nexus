# IDINO NOVA — Claude 파리티 로드맵 v1

기준일 2026-08-23. 근거는 4개 축(모델·추론 / 하네스·에이전트루프 / 기능표면·도구 / 계측·평가)의 제안 33건과 그 전수 반증 결과이며, 모든 %p는 반증에서 보정된 값만 쓴다. 원안의 %p는 폐기한다.

**컨텍스트 현행값 확정(코드 실측).** `config/vllm_launch.yaml` axmodel `max_model_len: 65536`이 유일 현행이다. 운영본 `nexus_config.112.yaml:131` `max_context_tokens: 61440`(2026-08-13 정정 의미론 — 입력+출력 총예산), 베이스·pc본은 49152(구 의미론 — 입력 상한). 베이스 yaml :564의 "32768 ≤ max_model_len(32768)" 주석은 구세대 잔재이고, pc본(5090)에서는 32768이 여전히 유효 불변식이다. 즉 "65536이 B200 현행, 32768은 베이스에선 잔재·5090에선 현행"이며, 이 세대 혼재 자체가 우선순위 7번(출력 에스컬레이션 정리)의 근거다.

## 1. 도달 가능한 상한 — 먼저 못박는다

전부 다 해도 넘지 못하는 지점부터 적는다. 요인은 셋이고 서로 다른 종류의 벽이다.

**표면의 상한은 인력이 정하고, 능력의 상한은 모델 가중치가 정하고, 컨텍스트의 상한은 물리(VRAM·네이티브 창)가 정한다. 이 로드맵의 어떤 항목도 가중치와 물리를 바꾸지 않는다.**

| 축 | 현재(코드 근거 추정) | 전부 실행 시 상한 | 못 넘는 이유 | 지배 요인 |
|---|---|---|---|---|
| CLI 기능 표면 | 55~65% | **~85%** | Claude Code는 월 단위로 신기능이 추가된다. 1인 팀의 재구현 추격은 상시 유지비이며, IDE 통합·확장 생태계·구독 UX는 재구현 범위 밖이다 | 인력·생태계 |
| Web 표면 | 50~60% | **~85%** | 동일. 추가로 웹 Bash 제거(보안 결정)는 의도적 미달분이다 | 인력·보안 결정 |
| Web API | 40~50% | **~80%** | Batch·Files·프롬프트 캐시 과금 제어 등 인프라성 API는 수요 없이는 서류 파리티이고, 있어도 vLLM 서빙 특성에 제약된다 | 인프라 |
| Code API | 25~35% | **~70%** | 플러그인 표면은 따라가지만 응답 품질이 모델 상한에 먼저 걸린다 | 모델 파라미터 |
| 단일파일 수정 | 70~85% | **~85~90%** | guided decoding·코더 프로필로 형식 오류는 0에 수렴시킬 수 있으나, 논리 오류는 못 고친다. 실측 근거 — 테스트 작성에서 Qwen3-Coder 0/3(경계조건 오독). 하네스는 경계조건 추론을 대신하지 못한다 | 모델 파라미터 |
| 다중파일 다중턴 agentic | 25~40% | **~50~60%** | 턴별 성공률의 복리 문제다. 턴당 성공률 95% vs 99%는 20턴 과제에서 완주율 36% vs 82%로 벌어진다. 하네스(서브에이전트·compact·STOP 훅)는 턴 수를 줄이고 오류 전파를 끊을 뿐, 턴당 오류율 자체는 가중치가 정한다. 프런티어 모델의 agentic 능력은 RL로 학습된 것이고 A.X-4.0은 프롬프트로 흉내 내는 중이다 | 모델 파라미터(지배), 컨텍스트(부차) |
| 한국어 문서·RAG | 85~100% | **100~110% — 유일하게 Claude 초과 가능** | 이 축의 상한은 Claude가 아니라 우리 검색 품질이다. 사내 코퍼스 접근·테넌트 격리·에어갭 준수는 Claude가 구조적으로 제공할 수 없다 | 데이터(우리가 우위) |
| 장문 컨텍스트 | 65536/1M ≈ 6% | **131072/1M ≈ 12~13%** | KV FP8 전환으로 131K까지가 물리 상한이다. A.X-4.0 네이티브 창(max_position_embeddings)이 131072라 그 밖은 학습되지 않은 영역이고, 1M의 KV는 FP8로도 ~160GiB라 전 모델을 퇴거시키고 단일 시퀀스만 돌려도 품질이 보장되지 않는다 | 물리(하드) |
| 속도(TTFT/TPS) | 측정 불능(화석 벤치) | 측정 후 판정 | LAN 로컬 서빙이라 왕복 지연은 유리하나 72B FP8 디코드는 프런티어 서빙 인프라 대비 열세 가능. 벤치 수리 전에는 어떤 주장도 하지 않는다 | 인프라 |

정직한 요약. **agentic 코딩에서 Claude와의 격차는 절반쯤만 하네스 문제다.** 나머지 절반은 72B FP8 + 30B MoE의 가중치 문제이고, 그 절반은 이 로드맵으로 닫히지 않는다. 반대로 한국어 문서·RAG는 이미 상한 근처이며 남은 일은 "넘었다"를 측정 가능한 명제로 만드는 것이다.

## 2. 검토했으나 제외 — 재제안 방지 기록

반증에서 죽은 제안 5건. 다음 세션에서 같은 아이디어가 다시 올라오면 이 표를 먼저 보라.

| 제외 제안 | 제외 사유(한 줄) | 부활 조건 |
|---|---|---|
| min_p·top_k 독립 배선(모델 #2) | 겨눈 결함군(긴 리터럴 붕괴)이 코더 라우팅·rep 1.05 실측(경로 6/6, 인자 5/5)·guided 재시도로 이미 흡수돼 실패 분모가 0 근처 — 독립 배터리 0.5일을 쓸 근거 없음 | 없음. 페이로드 배선 작업 자체는 우선순위 6번(코더 프로필)의 부속으로 흡수됨 |
| 도구 인자 guided decoding 상시화(모델 #4) | 이득 상한인 parse_error 잔여율이 미측정, 실사례는 기존 named 재시도가 이미 복구, "세션 단위 선제 강제" 폴백은 도구 선택 자유를 뺏는 설계 결함 | RunReport(우선순위 2번)의 parse_error 실측이 유의미(5%+)하게 나오면 1단계(vLLM 문법 제약 조사)만 재상정 |
| n-gram speculative decoding(모델 #7) | 주 수혜 트래픽(복사 중심 코딩 턴)이 이미 코더(활성 3B — 디코드가 원래 빠름)로 라우팅돼 앵커에 없고, 전 모드가 rep/freq 페널티를 써서 vLLM spec decode 병용 제약에 걸릴 개연성이 최고 | 앵커 문서 인용 턴의 지연이 실측으로 문제화되고 vLLM 버전의 페널티 병용이 확인될 때 |
| TOOL 턴 한정 A.X LoRA(모델 #8) | 게이트 분모(1차 시도 tool_call 성공률) 미측정 상태에서 +10%p 게이트가 산술적으로 성립 불가능할 수 있고(기존 실측은 기준선 90%+ 시사), 목록 최대 공수(2~4주)이며, TOOL 클래스는 코딩 전용이 아니라 문서 분석 품질까지 영향권 | parse_error 잔여율 ≥5% 실측 + 코더 프로필(6번) 완료 후에만 재상정. 그 전까지 기대 상승폭 0 취급 |
| /v1/embeddings 프록시(표면 #8) | 파리티 축(Anthropic API)에 없는 항목이고 소비자 수요 미확인(AgentHub 계약 미확인), 유일한 실부담이 내부 공유 임베딩 서버 지연 전이라는 순리스크 | AgentHub 등 연동 계약 문서에 임베딩 요구가 명시되면 0.5~1일 제안으로 재상정(메커니즘·에어갭·VRAM은 이미 검증됨) |

**반증으로 정정된 사항(생존 항목 내부의 축소·조건 — 역시 재논쟁 방지용).**

- with_retry는 안 A(query_loop 백오프)만. 안 B(스트리밍 제너레이터 재진입)는 비권장 확정.
- STOP 훅의 "검증 실행률 0/6 → 80%" 근거는 폐기(그 실측은 tool_use=0 사례이고 코더 교체 전 것). 기대치 +1~4%p로 하향, BLOCK 사유의 messages 주입 코드가 필수 추가분.
- transcript 스캐너에서 도구실패율은 산출 불가(도구 결과는 transcript에 안 실린다). 지표는 턴수·토큰·중단률·재전송 4종으로 축소.
- RAG-KO 채점 엔드포인트는 `/v1/chat/completions`가 아니라 네이티브 `/v1/chat`이다. knowledge_sources 인용은 네이티브 응답에만 실린다.
- Claude 기준선 러너는 `--permission-mode acceptEdits`로는 Bash 승인이 안 돼 분모가 눌리고 파리티가 부풀어진다. Bash 허용 플래그(또는 격리 스크래치에서 전체 승인)로 실행해야 성립한다.
- 서브에이전트 부활은 `DISALLOWED_TOOLS_FOR_AGENTS`의 'TaskCreate/TaskStop'(구식 이름) 문제를 먼저 고쳐야 한다. 실제 도구명 'Task' 추가가 선행이다.
- 출력 16384 복원은 동적 클램프가 전제조건이다(pc/5090 창 32768에서 즉시 위반 방지). "설정 3본 동일 잔재"는 부정확 — 112본 주석은 이미 65536 기준으로 갱신돼 있다.
- KV FP8+131K는 "청킹 결함 해소"가 아니다. 청킹 경로는 이미 정상 동작하며, 이 항목은 그것을 통짜 처리로 대체하는 품질·지연 개선이다.
- 원안 %p는 전부 보정치로 대체됐다. 대표적으로 코더 프로필 +5~10 → +0~3, 서브에이전트 +8~12 → +4~8, SC는 축 전체 +1%p 안팎, Code API model 배선 +8~15 → +3~6.

## 3. 의존관계 판정

**핵심 판정. 계측은 "착수의 선행조건"이 아니라 "채택 판정의 선행조건"이다.** 29건 중 절반가량은 기존 배터리(코딩 bakeoff 3과제, 금액 자릿수 15케이스, needle 하네스, 표면 e2e 34건, unit 스위트)로 자체 게이트가 완결되므로 계측 완성을 기다릴 필요가 없다. 그러나 agentic %p를 주장하는 항목의 채택/폐기 판정은 NovaBench 없이 불가능하다. 따라서 Wave 1은 "계측 구축"과 "무위험 설정부채 청산"의 병행이 맞고, 계측이 끝날 때까지 전 작업을 멈추는 것은 틀리다.

## 4. ROI 통합 우선순위 — 축 무관 단일 목록

정렬 기준은 (확실성 × 보정 효과) / 공수이며, 다른 항목의 판정을 해금하는 계측 항목은 그 해금 가치를 효과로 친다.

## 6. 가장 큰 단일 레버 하나

**NovaBench-Replay + Claude 기준선(우선순위 1번+10번 — 동일 태스크·동일 채점기의 한 시스템)이다.**

근거. 이 프로젝트에서 실제로 품질을 움직인 사건은 전부 측정에서 나왔다. rep_penalty 1.0이 degeneration의 근본 원인임을 찾은 것도 15케이스 실측이었고, 반대로 측정이 없던 곳에서는 단위 테스트 2,600개가 통과하는 동안 실서버 404가 15일 방치됐다. 이번 반증 라운드 자체가 그 증명이다 — 33건 제안 중 5건이 죽고 대부분의 %p가 반토막 난 이유는 하나같이 "분모를 재지 않았다"였다. 벤치 없이 Wave 2를 강행하면 서브에이전트·STOP 훅·compact 개선의 채택 판정이 전부 인상비평이 되고, 과거 경험상 검증 없는 변경은 조용히 회귀한다.

그 하나만 하면 얻는 것.

- "다중파일 agentic 25~40%"라는 폭 15%p짜리 추정이 재현 가능한 실측 기준선으로 바뀌고, Claude 분모가 동결돼 "파리티 N%"가 계약 가능한 문장이 된다.
- 태스크별 pass·턴수·도구 오류·토큰이 남아 실패의 원인 분해(모델 붕괴인가, 잘림인가, 라우팅 미스인가)가 가능해진다.
- 이후 모든 제안 — 이 문서의 28건이든 다음 세션의 새 아이디어든 — 이 같은 잣대로 채택·폐기된다. 제외된 LoRA·guided 상시화의 부활 조건도 이 계측이 판정한다.

그 하나만 하면 못 얻는 것.

- **파리티는 1%p도 오르지 않는다.** 수치는 정확해질 뿐 격차는 그대로다.
- 확실성이 입증된 즉효 수리 — 한글 5~8배 과대추정이 만드는 조기 압축(3번), Qwen3-Coder에 실린 A.X용 샘플링(6번), Code API의 model 무시(5번) — 가 전부 방치된다. 이것들은 벤치 없이도 고칠 수 있고 고치면 바로 이득인 항목들이다.
- 컨텍스트는 65536에 머물고, 문서 통짜 8만자도, Web API 표준 정합도, 서브에이전트도 없다.

그래서 결론은 "하나만 한다면 계측, 실제로는 Wave 1 패키지"다. Wave 1은 계측(3~5일)과 무위험 수리(합계 5~7일)를 병행하도록 설계돼 있고, 두 트랙은 서로를 기다리지 않는다. 계측은 격차를 좁히는 레버가 아니라 나머지 모든 레버가 헛돌지 않게 하는 받침점이며, 이 프로젝트의 이력이 증명하듯 받침점 없는 레버는 이미 두 번 부러졌다.
