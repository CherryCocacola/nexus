## P1 — 가드가 멀쩡한 표를 잘랐다

8열 테스트케이스 표 1800자를 실제 `DegenerationMonitor` 에 먹이면 판정이 True 다.
신호를 분해하면 A(동일라인) 1회·C(이모지) 0.000·D(전역) False 이고 **B 만 발화**한다 —
공백 제거 후 최빈 4-gram `'----'` 457회, 비율 **0.609** > 임계 0.45. 표 구분선이다.

수정: 4-gram 계산 전 표 구분선 행을 제외한다. 판정은 정규식 앵커가 아니라
**문자 구성**으로 한다(`|` 와 `-` 를 둘 다 포함하고 나머지가 표 구조 문자뿐).

앵커를 버린 이유가 중요하다. `_tail` 은 델타 조각을 이어붙인 window 라 줄이
반토막 난 상태로 검사된다. 특히 구분선을 **생성하는 도중**에는 마지막 줄이 늘
`|-----|--` 형태로 미완성이라 끝 앵커에 안 걸린다. 실측 대조:

```
                수정전(앵커)      수정후(문자클래스)
정상 8열 표      0.014 통과        0.014 통과
tail 미완성      0.862 오탐!       0.029 통과
head 반토막      0.608 오탐!       0.016 통과
진짜 대시 폭주    0.995 탐지        0.995 탐지
```

알려진 사각: `|-|-|-|-…` 형 폭주는 제외돼 B 로 못 잡는다(관측 사례 없음, A/D 가 부분 커버).

★회귀 테스트는 반드시 **소청크(20~40자) 스트리밍 재생**으로 한다. `check_every`
케이던스와 `_last_check_len` 상태 때문에 **판정이 feed 입도에 의존**한다 —
단발 feed 테스트는 이 클래스의 버그를 구조적으로 통과시킨다.

## P2 — 모델이 마크다운 이스케이프를 JSON 에 넣는다

step5 재시도에서 파싱 실패 12건. `Invalid \escape` 7 / `Expecting ',' delimiter` 3 /
`Unterminated string` 2. 앞의 7건은 `no\_line\_products\.csv` 처럼 마크다운
이스케이프가 JSON 문자열 값에 들어간 것이다. 길이가 원인이 아니라 길수록 이런
문자가 나올 확률이 높은 것뿐이다.

수정: 3단 폴백의 3단계로 escape 복구를 넣었다(`\X` where X ∉ `"\/bfnrtu` → `\X`,
그리고 hex 4자리 없는 `\u`). 복구 후 **strict=False 로** 파싱한다 — 이스케이프 붕괴와
제어문자 혼입이 한 인자에 공존할 수 있다.

★뒤의 5건(문자열 경계 파손)은 **일부러 복구하지 않는다.** 경계를 추측해 고치면
조용히 다른 내용을 파일에 쓰게 된다. 빈 dict → 스키마 거부 → guided 재시도라는
기존 fail-closed 경로가 정답이다. 이 경계를 코드 주석과 테스트로 못박았다.

## P3 — 절단본이 exit 0 으로 나갔다

신호 흐름을 추적하면 마지막 한 칸만 비어 있었다.

```
워치독      degeneration 감지 → mark_cut()                    신호 있음
query_loop  was_cut → 재생성 1회 + SYSTEM_WARNING             작동함
            재생성본도 붕괴 → 예산 소진 → **로그만 남김**       ← 구멍
ask()       ERROR·TEXT_DELTA 만 봄 → SYSTEM_WARNING 무시       ← 구멍
```

수정:
- `StreamEvent.error_code` 에 안정적인 코드를 싣는다(문구 매칭은 문구가 바뀌면 깨진다).
  `STREAM_DISCARD_RETRY`(앞 출력 폐기, **실패 아님**) / `STREAM_TRUNCATED`(불완전 출력, 실패).
- 방출 지점 3곳 — 붕괴 재생성 / 예산 소진(신설) / **타임아웃 재시도**.
  타임아웃 재시도도 같은 이중 출력 구조라 같은 코드를 단다.
- `ask()` 는 비 TTY 에서 **버퍼링**한다. stdout 구분자를 넣으면 파이프 파싱이 또
  깨지므로, 아예 모았다가 끝에 한 번에 내고 폐기 신호에 버퍼를 비운다.
  answer_parts 도 함께 리셋해 사후 검증기가 합본을 대조하지 않게 한다.
- REPL 은 `⚠` 한 줄로 표시한다(박스는 본문 흐름을 두 동강 낸다).

★최대 회귀 위험은 **타임아웃 재시도 성공을 exit 1 로 오배선**하는 것이다 —
정상 복구가 CI 실패로 둔갑한다. 테스트로 분리 고정했다.

## P6 — Edit fuzzy 가 파이썬 블록을 옮겼다

step6 에서 `return orders` 가 `except` 블록 안으로 들어가 로더 3개가 None 을
반환했다. 문법은 유효해서 구문 검사도 통과한다.

구조적 원인: fuzzy 폴백은 **모델이 공백을 이미 틀렸을 때만** 발동하는데, 교체는
같은 모델이 쓴 `new_string` 의 공백을 100% 신뢰했다. 못 믿을 공백인 모집단을
골라내서 그 공백을 믿는 구조다.

수정: 교체 전에 들여쓰기를 파일 기준으로 재정렬한다.
1. old ↔ new 에서 모델이 **바꾸지 않은 줄**을 찾는다.
2. 그 줄들이 요구하는 이동량을 모은다. 전부 같으면 그게 delta(블록이 통째로 밀린
   경우 — 교정 가능). **서로 다르면 블록 내부 상대 들여쓰기가 틀린 것이라 거부**하고
   파일 원문을 에러에 실어 준다.
3. 새로 추가·수정된 줄은 delta 만 적용해 통과 — 줄 수 불일치가 문제에서 빠진다.

★delta 를 `old_string` 기준으로 잡으면 안 된다. 모델이 old 의 들여쓰기는 틀리면서
new 에는 파일과 같은 올바른 들여쓰기를 쓰는 경우가 흔하고(기존 HTML 테스트가 그
케이스였다), 그때 old 기준 delta 는 멀쩡한 편집을 밀어 버린다. 기준은 **파일과
유지된 줄**이다.

## P7 — 경고로는 못 막았다

P5 를 넣고 실서버로 재검증했더니 **같은 실패가 재발했다.** 모델이 문서를 채팅에
출력하고 "작성했습니다"로 끝냈고, 경고는 붙었지만 파일은 여전히 없었다.
경고는 탐지지 예방이 아니다.

STOP 훅 호출부는 `query_loop.py` 에 **이미 있었다.** 안 돌던 이유가 셋이다.
  ① `hook_manager` 가 부트스트랩에서 만들어지지 않아 항상 None(dead code).
  ② `QueryEngine` 이 받아서 저장만 하고 `query_loop` 으로 넘기지 않았다.
  ③ metadata 에 도구 정보가 없어 판단 근거 자체가 없었다.

수정: 셋을 잇고 내장 훅을 신설했다.
- 판정 조건 — 파일 작성 주장이 있고(파일 표지 포함), **성공한** 쓰기 도구가 0건이고,
  차단 상한에 아직 도달하지 않았을 때 BLOCK.
- 근거는 "마지막 사용자 메시지 이후"로 본다. 모델이 세 턴 전에 파일을 쓰고 지금은
  요약 중일 수 있어, 턴 하나만 보면 정상 케이스를 오탐한다.
- **차단 사유를 대화에 주입한다.** 없으면 모델은 왜 턴이 이어지는지 모른 채 같은
  답을 반복해 차단이 루프로 바뀐다.
- 세션당 상한 2회. 끝내 안 쓰면 사후 검증 경고가 사실을 남기고 종료한다.

★권한 파이프라인의 `components["hook_manager"]`(bootstrap :338)는 **건드리지 않았다.**
거기에 꽂으면 Layer 4 PRE_TOOL_USE 가 활성화돼 shadow 모드의 "관측 전용" 보장이
깨진다(그 자리 주석의 경고 그대로). STOP 전용 매니저를 따로 뒀다. Layer 4 배선은
별개 결정 사항이다.
